03 / Case investigation

Open the case chapters.

Each chapter reveals a symptom, the test used to investigate it, the evidence, and the fix. Open them one by one like an incident-response log.

01The Countdown — a campus-wide mystery

Time: 8:50 AM. The online examination is about to begin. Students connect to campus Wi-Fi, but Lab A cannot open the portal. In Room B, the homepage loads, but answer submissions time out.

First clue: Library students can open the portal and submit answers normally. So the examination server is not completely down.

Networking focus: Wi-Fi connectivity, client configuration, and network topology.

02The Wrong Gateway — DHCP configuration

Lab A devices have IP address 10.20.5.25 and subnet mask 255.255.255.0, but their default gateway is 10.20.5.1. The correct gateway is 10.20.5.254.

ipconfig /all
ping 10.20.5.254
Root cause: The Lab A DHCP scope is providing the wrong default gateway address.

Fix: Correct the DHCP gateway setting and renew client IP leases.

ipconfig /release
ipconfig /renew

Why it works: The default gateway is the next-hop router used when a device sends traffic outside its own subnet.

03The Packet That Took the Wrong Road — DNS

After the gateway is corrected, some computers still open an old maintenance page instead of the live examination portal.

nslookup exam.college.edu

DNS returns 10.30.1.40, but the live examination server is 10.30.1.50. The DNS A record is stale.

Root cause: exam.college.edu still points to the old portal server.

Fix: Update the DNS A record and flush local DNS caches.

ipconfig /flushdns
nslookup exam.college.edu

Why it works: DNS translates a domain name into an IP address. Correcting the record sends browsers to the correct server.

04The Connection That Wasn't Enough — server bottleneck

The portal now loads, but when hundreds of students submit answers together, some requests are delayed or fail.

The team captures packets and checks server logs. TCP handshakes succeed, but retransmissions, duplicate acknowledgments, and HTTP 504 timeout responses appear during submission.

Root cause: The application server and database cannot handle the sudden number of simultaneous submissions.

Fix: Increase the application-worker limit and database-connection pool within tested capacity limits.

Why it works: A successful TCP connection does not guarantee that the web application can process every request quickly. TCP provides reliable transport, but the application must still have enough capacity.

05The Rule Nobody Checked — firewall false positive

Most students can submit answers, but requests from one approved browser extension receive HTTP 403 Forbidden responses.

403 Forbidden
Rule ID: BLOCK_SUSPICIOUS_HEADER
Destination: exam.college.edu/submit
Root cause: A broad firewall/reverse-proxy rule incorrectly blocks a legitimate submission request.

Fix: Add a narrow, approved exception for the verified extension without disabling the security rule.

Why it works: The firewall continues blocking suspicious traffic while allowing legitimate examination submissions.

06Forty-Seven Minutes Later — verification

Time: 9:47 AM. The team verifies every layer of the service: Wi-Fi association, DHCP settings, gateway reachability, DNS resolution, TCP port 443, portal loading, answer submission, and confirmation pages.

ipconfig /all
ping 10.20.5.254
nslookup exam.college.edu
tracert exam.college.edu
Test-NetConnection exam.college.edu -Port 443
Case closed: Four independent faults were identified and safely corrected. Full examination service was restored in 47 minutes.

Case file #047 • 8:50 AM

The morning the examination portal disappeared

It was 8:50 a.m. on an important examination day at the college. Students were entering their classrooms, opening their laptops, and connecting to the campus Wi-Fi. The online examination was scheduled to begin at 9:00 a.m. Everything seemed normal — until the first complaint arrived.

“Ma’am, the examination portal is not opening!” shouted a student from Lab A. Almost at the same time, another message came from Room B: “The website opens, but our answers are not getting submitted!”

Within minutes, the complaints started coming from different parts of the campus. The network team initially suspected that the examination server had crashed. But one detail did not fit: students sitting in the Library could open the portal and submit their answers without any problem.

That was when Meera, the network investigator, stepped in. “If the entire server were down, nobody would be able to use it. We need to stop guessing and follow the evidence. Let's check the network one layer at a time.”

Clue 1: The Library could use the portal successfully. The problem was not a complete server shutdown. Different locations were experiencing different symptoms.

9:05 AM — The wrong road

Meera began with Lab A. The students were connected to Wi-Fi, so she checked their IP configuration using ipconfig /all. The computers had an IP address of 10.20.5.25 and a subnet mask of 255.255.255.0. But something was wrong with the default gateway.

“The gateway is 10.20.5.1, but it should be 10.20.5.254,” Meera noticed. “The default gateway is like the exit gate of a campus. If a computer wants to communicate outside its own network, it sends the traffic to this gateway. These computers are being given the wrong exit.”

She checked the DHCP configuration and found the first fault: the Lab A DHCP scope was providing an incorrect default gateway. The team corrected the DHCP setting and renewed the clients' IP leases using ipconfig /release and ipconfig /renew.

Lab A could now reach the correct gateway. But the investigation was far from over.

9:14 AM — The address that lied

Some students could now reach the network, but their browsers were still opening an old maintenance page instead of the live examination portal.

Meera ran nslookup exam.college.edu. The result showed the address 10.30.1.40. She compared it with the live examination server address: 10.30.1.50.

“We have another problem. DNS is giving the computers an old address,” she explained. “DNS works like a contacts list. We type a website name, and DNS finds the IP address connected to that name. Here, the contacts list is outdated, so some browsers are being directed to the old server.”

The team found a stale DNS A record for exam.college.edu. They updated it to point to the live server and cleared the local DNS cache with ipconfig /flushdns. After checking the name again, the correct address appeared.

Clue 2: The domain name was resolving to 10.30.1.40, while the live portal was at 10.30.1.50. The DNS record was stale.

9:22 AM — Connected, but still not working

The portal was now opening for more students. For a moment, the team thought the problem was solved. Then another wave of complaints arrived: “My answer is taking too long to submit!” and “The page is showing a timeout!”

This time, Meera and the team examined packet captures and server logs. They found that TCP handshakes were succeeding, but during the rush of hundreds of simultaneous submissions, there were retransmissions, duplicate acknowledgments, and HTTP 504 Gateway Timeout responses.

Meera explained, “TCP can establish a reliable connection between the computer and the server. But that does not mean the application has enough capacity to process every request quickly. Imagine a restaurant where the entrance is open, but the kitchen has too many orders. Customers have entered, but their food is delayed.”

The application server and database were struggling with the sudden load. The team increased the application-worker limit and database-connection pool within tested capacity limits. The portal became more responsive, and submissions started completing more reliably.

9:31 AM — The rule that blocked the right person

Most students could now submit their answers. However, a few requests from an approved browser extension were still being rejected. The browser displayed 403 Forbidden.

Meera checked the firewall and reverse-proxy logs. The evidence showed a rule named BLOCK_SUSPICIOUS_HEADER blocking a request to exam.college.edu/submit.

“A firewall protects a network by checking traffic against security rules,” Meera said. “But a rule can sometimes be too broad. This one is treating a legitimate request as suspicious.”

The fourth fault was a false positive caused by an overly broad firewall/reverse-proxy rule. The team did not switch off the security rule. Instead, they added a narrow, approved exception for the verified browser extension. Suspicious traffic remained blocked, while the legitimate submission request was allowed.

Clue 4: The HTTP 403 response and firewall log identified a security rule false positive — not a DNS, gateway, or server-capacity problem.

9:47 AM — Forty-seven minutes later

By 9:47 a.m., the team had corrected all four faults. But Meera knew that changing settings was not enough. The service had to be tested from beginning to end.

The team checked the Wi-Fi connection, DHCP configuration, gateway reachability, DNS resolution, TCP port 443, portal loading, answer submission, and confirmation pages. They used commands such as ipconfig /all, ping 10.20.5.254, nslookup exam.college.edu, tracert exam.college.edu, and Test-NetConnection exam.college.edu -Port 443.

One by one, the checks passed. Students could open the correct portal, submit their answers, and receive confirmation. The examination service was finally restored.

Meera looked at the incident log and summed it up: “It looked like one big network failure, but it was actually four independent faults — a wrong DHCP gateway, a stale DNS record, an application-server bottleneck, and a firewall rule that blocked a legitimate request. We solved it because we followed the evidence layer by layer.”

CASE CLOSED — 9:47 AM. Four faults. Four targeted fixes. One examination portal restored in 47 minutes.

The lesson: a connected device does not automatically mean a working application. Good network troubleshooting means identifying exactly where communication fails, proving the cause, applying a safe fix, and verifying the complete service.

08 / What the incident teaches

Lessons from the outage.

The biggest lesson: a working Wi-Fi icon does not prove that the whole application is working.

01

Check layer by layer.

Do not jump to the conclusion that the server is down. Test the client, gateway, DNS, transport, and application.

02

Separate symptoms.

Different rooms and different failure patterns can point to independent faults, even during one incident.

03

Fix safely, then verify.

Correct the exact DHCP, DNS, capacity, or firewall issue. Avoid broad changes that create new security risks.
